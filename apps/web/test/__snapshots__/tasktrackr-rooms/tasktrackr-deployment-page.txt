It ships as two services: a Python API and a Node process that serves the front end and forwards /api to the API. Three configuration files are scaffolded and incomplete, and the runbook is yours to write in the Runbook tab.In api/Dockerfile the base image, the environment and the volume are set. Replace the three TODO(learner) markers: set a WORKDIR for the app; COPY what the image needs (requirements.txt for the pip install below it, api/ and ops/ to run at all, and docker-compose.yml, because ops/selfcheck.py reads the deployment this image belongs to); and define an ENTRYPOINT in exec form, so that docker run tasktrackr --selfcheck reaches api/main.py. web/Dockerfile beside it is finished and locked. It is the worked example: two stages, the build tools left behind in the first. Read it when a line will not come.In docker-compose.yml both services, one network and one named volume are wired. Replace the two TODO(learner) markers: give api a healthcheck the web service can wait on (web already declares condition: service_healthy, and the api image carries python3 and nothing else, no curl and no wget), and point API_URL at the api service. Inside a compose network a service is reachable by its own name on a port it exposes; localhost inside a container means that container.In .github/workflows/ci.yml there are three jobs, because this application has two suites and two images. Checkout, the runtime and the install are wired in each of them; what is missing is the line that runs something. In test, add a step that runs the API suite, which package.json calls test:api. In web, add a step that runs the front-end suite, test:web. In build, add a step that builds both images: one build per Dockerfile, each with -f because both are built from the project root, or one compose build for the pair. That job already needs both suites, so a red test never reaches it.The Runbook tab holds the runbook an operator reads at 3am, in five sections. Environment: each setting's name, what it controls and its default; TASKTRACKR_DB and API_URL are the two an operator changes, and PORT and HOST are worth an entry each. Health checks: a command that proves the deployment is alive and the output that proves it; the check compose itself waits on and the selfcheck that reads the whole deployment are both good answers. Rollback: the steps that get the previous known-good images back, in order, and what a rollback does not undo. Data: where the database lives, which commands keep it and which delete it, and how to take a backup and put one back. Incident: written for you from the drill page when you close INCIDENT-1. Check the runbook lists what the floor still asks for.Deploying is the worked example of an operator's line: docker compose up -d --build builds both images, starts api, waits for it to report healthy, then starts web on port 5173. Nothing else is needed on the host.Press Run selfcheck to check the saved configuration. The isolated runner compiles the Python source, reads the launcher from your api/Dockerfile ENTRYPOINT or CMD and WORKDIR, and invokes it with the project's --selfcheck argument. ops/selfcheck.py imports the Flask application, initializes the SQLite schema, checks that the Compose file gives web an API_URL naming a declared service and port, and reports whether a web bundle exists. Its success line reads selfcheck: web reaches api, 13 routes, 5 tables, and there web reaches api means the declared Compose address is consistent: no network request is made. This local check does not build either Docker image, install the Dockerfile's dependencies, execute GitHub Actions, start Compose services, or prove live HTTP health. A real release also needs successful image builds, live service checks and a versioned release record; do not claim those from this selfcheck.The drill page carries INCIDENT-1. Start it once your selfcheck passes: it runs the same isolated check against a faulted copy of your compose file and records the output. The symptom on the day was the whole application loading with every page empty, while the API was healthy and its logs were quiet. Read the output and name the setting at fault, check your own docker-compose.yml for the same mistake, run the health check against your own files, then close the incident on the drill page with the root cause naming the setting, the fix you made, and one action item. The review reads the incident.What good looks like: every runbook entry carries a real command or sentence, not a name alone; both suites run in CI, so a red test in either language fails the pipeline, and the job that builds the images waits on both of them; and the incident names the setting, API_URL, and the line that changed, not just that the site was broken.Ask the mentor why instruction order matters in a Dockerfile, what exec-form ENTRYPOINT changes, why a service name works inside a compose network where localhost does not, what a healthcheck can run inside an image that carries only python3, or what a rollback leaves behind on the volume. It explains and critiques; the configuration lines are yours. When you are ready, press Submit PR-5.
