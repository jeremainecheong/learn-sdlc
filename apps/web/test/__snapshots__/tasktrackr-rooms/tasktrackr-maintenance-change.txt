The ticket in the Request tab says what it asks for and how the change will be accepted.The codebase is the finished one. Lists, tasks, tags, filters and the overdue report all work, and the front end reads them. Your job is to add the new capability without breaking any of it.In api/repository/comments.py, implement add_comment(conn, task_id, author, body) and list_comments(conn, task_id). add_comment stores one comment and returns it in the shape the contract publishes: id, task_id, author, body and created_at. An unknown task raises KeyError, in either function. An empty author or an empty body raises ValueError, and whitespace alone is empty. list_comments returns the comments newest first.In api/routes/comments.py the blueprint is registered and the two handlers are yours. GET /api/tasks/{id}/comments answers 200 with the comments, or 404 task_not_found. POST /api/tasks/{id}/comments answers 201 with the comment, or 400 invalid_comment, or 404 task_not_found. api/routes/tasks.py is the worked example: it turns KeyError into a 404 and ValueError into a 400, and builds both with fail(), so every error this API sends has one shape.The task row has to show how many comments a task carries, so every task the API returns needs a comment_count. That lives in TASK_SELECT in api/repository/tasks.py, and that one query is read by get_task, list_tasks and overdue_tasks, each of which adds its own WHERE and ORDER BY. So the count has to come back as one value per task, without changing how many rows the query returns; tag_names, a few lines below, already does exactly that against another table. A join in the FROM clause is the obvious move and the wrong one. LIST_SELECT, which computes each list's task_count and open_count, is separate and does not change. The regression suite tells you, and you can run it yourself.In web/src/components/TaskRow.tsx a task that carries comments wears a badge, 1 comment or 4 comments, and a task with none wears nothing. The badge is a span with className badge badge-comments and data-testid comment-count, in the task-main block beside the overdue badge, which is the same shape a few lines above.Two contracts travel with the change. shared/contract/api.json is the published HTTP contract: add listComments and addComment in the shape of their neighbours, and the error code addComment answers with. design/contracts.json holds the operations you promised in the design phase, seeded when this phase unlocked: add the two comment operations, their inputs, what they return and the error cases. The conformance ledger holds your code against it.What 2.0.0 shipped: lists, tasks and tags over a SQLite database with foreign keys enforced; eleven HTTP operations under /api, published in the API contract; three screens behind a hash router; the overdue report, open tasks strictly past their due date, most overdue first, with the day a parameter; two containers and a compose file with a healthcheck and a named volume; the selfcheck; and a seed script. The web service proxies /api, so the application needs no CORS. The comments table is already in api/schema.sql, created by api/db.py, and nothing reads or writes it yet.Record the change in the change request as you go: in the Request tab, the operations, screens and files it touches; in the Contract tab, the two operations as contract amendments; in the Checks tab, the tests and the acceptance items each covers; in the Release tab, the 2.1.0 release, its summary, the change lines with the acceptance items each covers, and how to roll it back, written for the person who upgrades. Say truthfully whether a schema change is needed.On submit, a sealed suite runs your new behaviour and a regression suite over everything the earlier phases shipped, across both layers, pooled: a change that costs a regression scores less than no change at all. The visible tests are tests/test_comments_api.py, a three-question smoke of the change, tests/test_lists_api.py and tests/test_tasks_api.py, the regression suite, and web/src/components/TaskRow.test.tsx. Static analysis checks that no TODO markers are left and that complexity stays low. Keep the change small and local.What good looks like: the new functions read like their neighbours, with the same lookup helper for the unknown-task case, the same _to_comment on the way out, and no second copy of a check that already exists; the regression suite is green before you ever press Submit PR-6; and nothing outside the files the request names has changed.Ask the mentor how to scope a change safely, what a count in a composed query has to look like, or why regression tests belong in a maintenance change; it will not write the SQL, the routes or the badge for you. Press Run regression tests as you work, and Run app to see the count on a real row. When you are ready, press Submit PR-6.
